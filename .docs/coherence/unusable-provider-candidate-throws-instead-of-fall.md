## Consistency and achievability

All six outcomes, four stories, seven tasks and 24 criteria are covered. The plan introduces no change-set ADR. No gap, contradiction, oscillation or outside-diff requirement was found.

The setup/runtime boundary is representable: a normalized branded pre-invocation capability error advances the existing candidate loop; no invocation across the full list yields providerSetupExhaustion; any actual invocation prevents that classification. Tasks 1–2 own the source classification and list accounting, and Tasks 5–6 retain the result across the ordinary, one-shot and auxiliary input boundaries before retry/domain decoding. This fulfills outcomes 2 and 4 without overriding outcome 5. Scalar exhaustion is grounded in Task 2 and caller propagation in Tasks 5–6.

Cleanup is an independent authority: Tasks 3–4 release preparation-owned resources and preserve cancellation/safety refusals. Allocation failure remains an ordinary failure; the Task 3 release check does not authorize a next candidate after that failure. Task 4 expressly prevents subsequent invocation after failed cleanup or verification. The same spawnPermit and zero replacements provide the same-attempt constraint alongside Task 3’s original regression and Task 5’s captured native settings.

Preserved-behavior sweep: Tasks 2, 4, 5 and 6 exclude arbitrary errors, authentication, safety, policy loading, readiness and revoked authority from the new branch. Task 7 reports classified skips through existing observational callbacks and invocation-based consumers; it does not give sink failure retry authority or fabricate usage. Runtime retry preservation and setup-only stopping therefore do not oppose each other. Native model/effort attribution is grounded jointly in Task 5 invocation capture and Task 7 actual-invocation metering.

All acceptance inputs are controlled inside this diff’s tests with faithful external fakes. The completion checks name the producing classification, ownership, routing and consumer mechanisms; they do not depend on live provider availability or unstated later work. Additional live fallback failures remain unverified and are not acceptance requirements.
