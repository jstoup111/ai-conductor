**Outcome notes.**
- **outcome-3, "can only shrink".** The operator chose D5's reading on 2026-10-24 (architecture-review choice 3). Every allowlist entry that stops matching a live violation fails the check (story-3's stale-entry criteria). Adding an entry stays an explicit, reviewable act in the PR diff, and no diff-relative guard forbids it.
- **outcome-2 and outcome-4** are waived to their named homes. See the waiver file.

**Criterion rows.** These are generated from the plan's Coverage Check. That table passed independent coverage judgement on every row: round 1 passed 33 of 34, and round 2 passed the one revised claim.

**Achievability (§4g).**
- **Mechanisms.** Every cited check names `checkLayerRatchet`, `encodeAllowlistName`/`decodeAllowlistName` or `formatRatchetViolations`, and asserts the observable violation record (kind, file, line, edge, cycle, entry, reason) on an in-memory fixture. Tasks 1–7 build each rule into that one checker, and Task 8 runs it on the real tree.
- **Closed violation set.** The design's violation kinds are `upward`, `cycle`, `stale-entry` (`edge-missing`, `not-a-violation`), `malformed-entry`, `unclassifiable-file` and `unresolved-specifier`. Each required scenario has a representing value, and every "reports no violation" scenario is an asserted empty list.
- **Input boundary.** The real-tree read in Task 8 is the only source-to-map boundary. Its check enumerates "every `.ts` file under `src/conductor/src/`", which is the criterion's full quantified scope.
- **Constraints.** No check contradicts D5. The edge kinds, the staleness rule and the hand-addition policy are the operator-confirmed refinements, and D5's text does not forbid them.
