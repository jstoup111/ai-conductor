## Assumptions surfaced

- Outcome 2 reads "A Pi rate limit or usage exhaustion advances the candidate-fallback ladder exactly as claude/codex exhaustion does." Verified engine behavior: a Claude or Codex rate limit waits and retries the same provider, and Codex usage exhaustion suppresses Codex until its deadline while the dispatch that observed it waits for that deadline; only other dispatches in the window advance their ladder. Stories 1 and 2 give Pi exactly that behavior. The operator chose this parity reading on 2026-10-28 over an immediate fall-back of the current dispatch, which would be a provider-agnostic engine change for a separate intake.
- Tasks 11 and 12 assume the `Conductor` harness in `provider-execution-pi-fallback.test.ts` accepts an injected sleep and provider availability store, as its existing fallback tests construct them. Confidence 80%, inferred. If wrong, the tasks need a different harness, but the criteria stay deliverable. Not load-bearing for any verdict.

No row is `gap` or `fail`.
