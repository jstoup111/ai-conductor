## Notes

- **outcome-4 is a deliberate deviation.** The intake asked that small histories behave exactly
  as today. During explore the operator chose always-by-file delivery and accepted that small
  histories change delivery too. The track marker records it as the scope boundary, and the
  waiver records it as the outcome's disposition.
- **outcome-2** is met through files, not the prompt: every prior case is in the active
  snapshot or the resolved archive in full (story-2), and the skill directs when each is read
  (story-5). The agent reads the resolved archive on demand, which the operator approved.

## Architecture decision judgement (§4f)

- **adr-2026-09-07-durable-prd-widening-decision-reconciliation**
  - D7 (`task`, task-8): D7.4 removes the byte bound from the four history dimensions. Task 8's
    check requires `buildRemediationProjection` to return ok with each history dimension larger
    than the total limit and no fault naming any of them, and its first two checks keep the
    named-bound fault for required references, tasks, and the total. That is what D7.4 states.
  - D5 (`task`, task-10): D5's reconciliation mode must be unchanged. Task 10's check pins the
    reconciliation prompt to its existing form and requires no history file.
  - D1-D4, D6, D8-D10 (`no-change`): each governs PRD-widening authority, storage, capture,
    legacy handling, the native output schema, relationship commits, recovery ownership, or that
    ADR's own delivery boundary. This feature changes only how gap-plan history is delivered, so
    none imposes work here. D6's gap-plan output schema is untouched.
- **adr-2026-10-28-as-built-finding-reconciliation**
  - D2 (`task`, task-2): the amended Bound clause requires every case to reach the planner in
    full across the two files. Task 2's check requires every stored case in exactly one file and
    the union to equal the stored set; its first and fifth checks require each case in full.
  - D3 (`task`, task-11): every as-built disposition still carries a reconciliation result
    naming a prior case. Task 11's check requires a `recurrence` bound to an archived resolved
    case to be accepted, so moving resolved cases out of the prompt does not break D3.
  - D4 (`existing`): the admissible-effect rules are enforced by `validateRemediationPlan`
    against the in-memory projection, which this feature does not change.
  - D1, D5, D6, D7 (`no-change`): the case store, as-built authority, source recording, and the
    per-source spine event are all downstream of or separate from history delivery.

## Achievability (§4g)

Every criterion row was judged from the cited task's `Done when` checks alone. Each check names
its mechanism (`buildRemediationProjection`, the history writer, `renderRemediationPromptProjection`,
`projectionLimitFault`, `validateRemediationPlan`, the conductor halt class, or the skill text)
and the layer the criterion names: criteria that say a dispatch runs or a halt is written are
asserted through the conductor remediation route, not the projection builder alone. An
independent coverage judge passed all 44 rows after one revision round. No row is `fail`.
