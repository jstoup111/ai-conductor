## Technical Approach

The check is judgement, so it lives in the skill text; the engine already owns its bookkeeping. `resolveAsBuiltPolicy` (`src/conductor/src/engine/as-built-policy.ts`) turns `adrCompliance` off when the project has no APPROVED ADR, which gives the "no seams defined" degradation at SHIP for free. `resolveAsBuiltReferences` (`src/conductor/src/engine/as-built-contract.ts`) accepts a finding's `adr-decision` reference to any APPROVED ADR in the worktree, so a finding can cite a seam ADR the plan never cited. The as-built projection (`src/conductor/src/engine/as-built-projection.ts`) pre-selects only ADRs cited in the plan's `## Architecture Obligation Coverage` table plus ADRs the diff changes, so a bypassing feature's seam ADR is usually not pre-selected and the §12 text must tell the reviewer to read it on demand. The managed as-built step dispatches the skill through the `architecture_review_as_built` entry of `STEP_SKILL_INVOCATIONS` (`src/conductor/src/engine/skill-invocation.ts`), so the new §12 text reaches the managed reviewer unchanged. No engine file changes.

Definitions, stated once at the start of the new §4 block and reused by reference from §12: an *external system* is anything outside the project's own code that its production code reaches — a hosted API, another service, a database or queue, a model provider, or a command-line tool run as a subprocess. A *seam* is a boundary interface that an APPROVED ADR in the project's `.docs/decisions/` designates as the way production code reaches a named external system. The seam inventory comes only from APPROVED ADRs; DRAFT and SUPERSEDED ADRs, existing code, and diagrams define no seam (diagrams may help locate one an ADR defines). Existing code that already bypasses a seam is tech debt, not precedent (§1). Mechanical import-direction and layering rules between the project's own modules belong to the project's linter, not this check.

New boundaries and supersession. A new boundary passes only when no APPROVED ADR already gives that external system a seam, or when its ADR supersedes the existing seam ADR through the normal §7b lifecycle (human-approved, old ADR marked SUPERSEDED). At DECIDE, the ADR this review drafts for the new boundary must reach APPROVED before stories (§7b hard gate), so a superseding ADR the operator rejects leaves the bypass blocking. At SHIP, a new boundary passes when its APPROVED ADR is part of the same change and either covers a system no other APPROVED ADR gives a seam or supersedes that seam ADR; because a SUPERSEDED ADR defines no seam, a properly superseded seam no longer counts.

§4 block. Insert a new block titled `**Seam conformance (external boundaries):**` immediately after the `**Pattern consistency:**` block. Task 1 writes its opening (the definitions and the inventory rule above); Task 2 adds the directions: list each external system the proposed design's new production code reaches; for each, find the APPROVED ADR decision that defines its seam; when the design reaches that system directly instead of through the seam, record a blocking issue naming the external system, the ADR stem and decision, and the bypassing design element, and issue BLOCKED (resolved under §9 by routing through the seam or by a human-approved superseding ADR); pass a design that goes through the seam, extends the seam's own implementation, or introduces a new boundary under the supersession rule above; record nothing when no APPROVED ADR defines a seam for the system (including a project with no APPROVED ADR) and never infer a seam from existing code or from DRAFT or SUPERSEDED ADRs; leave import-direction and layering concerns to the project's linter. Because Lightweight Mode runs §4 in full, Medium reviews get the check without editing that section. Add one Verification item after the existing "Alignment checked against .docs/decisions/ and CLAUDE.md" item, beginning `Seam conformance checked:`.

§12 sweep. Insert a new bullet in the "Scope (only this)" list, immediately after the "For each enabled check, compare the shipped source…" bullet, with the bold label `Seam-conformance sweep (part of adrCompliance).` (the check name may be code-formatted). It refers back to §4's definitions and directs the reviewer to: run only when `adrCompliance` is on, and otherwise raise no seam finding; work diff-first — enumerate the production call sites the diff adds or reroutes (a changed target, import binding, or client of an existing call counts) that reach an external system, and when there are none, or they are only in test code or fixtures, treat the sweep as satisfied without searching the ADR corpus; for each such site, find the APPROVED ADR that defines that system's seam, reading APPROVED ADRs on demand because a bypassing feature's plan usually does not cite it and the engine's pre-selected governing ADRs may not include it; report every bypassing site with its `file:line` in BLOCKED findings governed by `<adr-stem> D<n>` of the seam decision (one finding per site, or one finding listing every site, as the existing exhaustive-sweep rule allows); raise nothing for a call through the seam, inside the seam's own implementation, or through a new boundary under the supersession rule above; raise nothing when no APPROVED ADR defines a seam for the system. Add two rows to the finding/class/governing-reference table, after the existing "Complying needs a changed or new architectural decision" row: `External-system call bypasses an APPROVED seam that already offers what the call needs` → `REMEDIABLE` → `<seam-adr-stem> D<n>`, and `External-system call bypasses an APPROVED seam, and complying needs a new or changed boundary decision` → `DESIGN` → `<seam-adr-stem> D<n>`. Add one Verification item after the existing as-built ADR-violation item, beginning `**As-built mode:** seam conformance`.

Project-agnostic wording. Inside both new passages, use only harness vocabulary — `adrCompliance`, `BLOCKED`, `REMEDIABLE`, `DESIGN`, `file:line`, `<adr-stem> D<n>`, `<seam-adr-stem> D<n>`, the harness-wide `.docs/decisions/` directory — and generic categories of external systems. No source path, file extension, module, port, interface, or vendor name of any repository appears. Keep wording provider-neutral (no host-specific tool or invocation); `test/test_provider_skill_contracts.sh` audits the shipped skills, including this one's delegation wording.

Verification approach. This change is natural-language skill guidance with no machine-readable or executable contract. Under `HARNESS.md` Behavioral Coverage at the Lowest Sufficient Layer and the `tdd` skill's Test Coverage Rule, such guidance is not executable behavior and must not be tested solely by matching its wording, so no task runs a RED/GREEN cycle or adds a wording test.
