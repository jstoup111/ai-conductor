# Track: Carry provider liveness on the build quiet warning

Track: technical

Scope boundary: Small fix for #1815, approved by the operator on 2026-09-06 (delegated). The build-progress watcher already holds every fact it needs except one that is sitting unread on disk — the provider-activity heartbeat the running dispatch stamps into the build worktree. Carry the newest such pulse's timestamp on the quiet-episode event the watcher already emits, and name its age on the daemon warning line that already renders that event. The quiet threshold itself, the heartbeat's own write cadence, the periodic build-progress heartbeat tick, the post-hoc stall breaker, the interactive terminal renderer, the OpenTelemetry attributes, the status dashboard, and the daemon's step-header naming are all outside this slice.

This is an engine and daemon-log observability correction; acceptance criteria live in technical stories rather than a PRD.

The operator approved carrying a factual activity timestamp over classifying the step as live-or-wedged inside the watcher, on 2026-09-06 (delegated). A timestamp needs no freshness threshold to be invented, keeps the judgement with the operator reading the line, and stays meaningful to every other consumer of the event; a boolean verdict would bake one repository's idea of "fresh" into the bus and hide the number the operator actually used to decide.

The issue's own hypotheses were weighed. Provider process liveness was rejected because the watcher runs in the conductor process and would have to shell out to a process table it has no handle on, and because the module that owns the heartbeat states plainly that heartbeat presence is never process-liveness authority. Provider rollout-file mtime was rejected because it is a provider-private path with no engine-side contract. A dirty-worktree delta was rejected as a second git probe on the hot poll path for a signal the heartbeat already summarizes. Moving the quiet threshold was rejected outright: the second desired outcome requires a wedged step to warn at least as promptly as it does today, so this slice qualifies the warning rather than delaying it.

Scope check: A — consumer-facing (engine and daemon-CLI code that any repository running the daemon executes; no self-host, validation-gate, release-gate, or repository-private convention is touched), so no rules file changes and no catalog registration; B — n/a (no new skill); C — provider-agnostic (the heartbeat is written by the shared dispatch path for every provider, and nothing here reads a provider name).

Event spine: Channel? no — nothing new observes, reports, or coordinates; an existing watcher reads an existing file and enriches an existing event. Concern: occurrence — the quiet episode. Verdict: extend the union with one additive optional field on the existing quiet variant. Exception: none needed. No sidecar, no second ledger, no timestamp stamped into an artifact for a later reader.

Verified foundation: the watcher's quiet branch emits its warning from a single site that already has the tick's counters and current task in hand, and its options already carry the feature worktree root and an injectable clock; the heartbeat module already exports a tolerant reader, a dispatch-ownership predicate that rejects a heartbeat left behind by an earlier step or an earlier dispatch, and a short age formatter; the daemon log renderer already has a case for the quiet event and already builds its line from the counters; the approved intra-step build-progress decision record fixes the watcher's lifecycle and the quiet determination, neither of which changes here, and its payload sketch lists optional fields, so one more optional field is additive rather than an amendment.
