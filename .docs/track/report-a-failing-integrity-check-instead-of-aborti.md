# Track: Report a failing integrity check instead of aborting the suite silently

Track: technical

Scope boundary: Small fix for #2160, approved by the operator on 2026-09-28 (delegated). Make the harness integrity suite report a failing check and run to its summary, and make any abort it cannot guard name itself. Raising, removing, or reordering checks, changing what any existing check asserts, and reworking the suite's file enumeration are outside this slice.

This is one of this repository's own validation gates, so acceptance criteria live in technical stories rather than a PRD.

The operator approved, on 2026-09-28 (delegated), guarding every status-passing call site plus a named abort diagnostic, over the two alternatives weighed: dropping `set -e` from the suite (rejected — it would silence every genuinely fatal error the option currently catches, and the suite has 22 regions that already toggle errexit deliberately), and reporting only through a trap without guarding the call sites (rejected — a trap names a line number, but the check itself still never reports PASS or FAIL and every later check is still skipped, so the summary stays wrong). The filer's hypothesis — guard each checked command so the reporter always runs — is one half of the accepted approach; the named abort diagnostic is the complementary half, because guarding known sites cannot cover the many other commands in the file whose failure would still exit it without a word. This is the same approach accepted for the earlier spec of this issue (PR #2334), which was closed only to serialize behind #2161; #2161 has since shipped and closed, so the blocker is gone.

Scope check: A — harness-repo-only (Step 1 signal 2: this repository's own validation gate, `test/test_harness_integrity.sh`); B — n/a (no new skill); C — provider-agnostic (a bash gate, no provider surface). No catalog registration is required. No rule in the shared harness contract is narrowed or replaced, so no consumer-convention sentence is owed. Event spine: no event, metric, span, log line, or report is added or changed; the suite keeps reporting through its own existing PASS/FAIL/summary output.

Verified foundation: `test/test_harness_integrity.sh:2` sets `-euo pipefail`; `assert()` at `:27` and `warn_check()` at `:52` take an already-computed status as their second argument; 17 call sites (`:75`, `:137`, `:1243`, `:1246`, `:1255`, `:1258`, `:1265`, `:1273`, `:1277`, `:1282`, `:1303`, `:1402`, `:1410`, `:1527`, `:1530`, `:1534`, `:1537`) run a bare command and then pass `$?`, so under errexit the shell exits before the reporter is reached. The suite already uses `set +e` at 22 places to capture a status deliberately, so status capture is established house style rather than a new idea. The summary and exit live at `:1920-1933`. The only existing trap is an `EXIT` trap set and cleared inside check 5c (`:574`, `:584`), so an `ERR` trap adds no interference. `test/test_harness_integrity_update_flow.sh` is the local precedent for a focused fixture spec over a gate, and check 22 (`:1660-1700`) is the precedent for wiring one.
