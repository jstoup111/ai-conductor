# Track: Authenticate OTLP export with env-referenced headers

Track: technical

Scope boundary: Small fix for #1939, approved by the operator on 2026-09-06 (delegated). Add one `otel.headers` key that carries a *reference* to a credential rather than the credential, resolve that reference from the process environment at config load, attach the resolved headers to the HTTP OTLP exporters, refuse a literal or malformed reference with a named error, and document the key alongside the other `otel` keys. Excluded from this slice, deliberately: additional at-rest secret sources (OS keychain, secret manager, permission-enforced file); gRPC credential carriage, which the installed exporter models as gRPC metadata rather than headers; classifying an unauthorized export response as an authentication-specific warning, which keeps today's bounded transport warning; and rendering `resolveOtelConfig`'s error strings to the operator, which is a pre-existing gap on every `otel` error, not a credential-specific one.

This is engine configuration and transport behavior shipped to every repository that installs the harness; acceptance criteria live in technical stories rather than a PRD.

The operator's stated requirement for this issue is that no literal credential is stored in harness configuration. The reference-only shape satisfies that mechanically: a string value under `otel.headers` is refused by name, so the insecure path cannot be the quiet default. Supporting exactly one source (the process environment) is the smallest shape that satisfies the requirement; the issue's "more than one secret source" bullet is knowingly deferred, and the resolution seam is a single function so a second source is additive later.

Scope check: A — consumer-facing (the `otel` block is shipped engine configuration; a repository with no daemon, no `.docs/` history, and no self-host build still gains authenticated export); B — n/a (no new skill); C — provider-agnostic (nothing here is Claude- or Codex-specific; the environment variable name is operator-chosen). Registration required: the `docs/reference/configuration.md` entry for the new key, and the test-side config consumer declaration.

Verified foundation: `ResolvedOtelConfig`'s enabled `otlp` variant carries `endpoint`, `protocol`, and `projectName` and no credential field; `buildExporters` passes only a URL to all four OTLP exporters; the installed HTTP exporter option type accepts `headers?: Record<string, string> | HeadersFactory` while the gRPC option type is `Omit<OTLPExporterConfigBase, 'headers'>` and takes `metadata` instead; `resolveOtelConfig` never throws and reports every invalid config as a disabled result plus a named error string; the accepted `otel` key list and the test-side consumer registry both enumerate the five existing keys, and the registry totality test fails for an accepted key with no declaration.
