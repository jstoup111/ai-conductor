Approaches weighed (filer hypotheses entered as candidates, not privileged):

- A (filer hypothesis 1 alone): retain join-satisfied siblings as `done` at the refusal exits. Rejected alone: it does not touch a sibling that a kickback restaged `stale`, so outcome 2 (stale member preserved on fan-out) stays unmet.
- B (filer hypothesis 2 alone): run the stale-preservation probe for stale members on fan-out. Rejected alone: it covers the observed incident (the sibling was already `stale` from an earlier kickback) but not a first-round refusal, where the passing sibling is still `pending` and would re-dispatch.
- C (not from the filer): restage the join-satisfied siblings as `stale` at refusal exits, plus B, so every resumed sibling passes through the probe. Rejected: it creates a second retention meaning beside the approved `done` retention for the same fact (adr-2026-07-10-validation-group-join D2 as amended by #1425), and overloads `stale`, which today means an upstream change invalidated the step.
- D (not from the filer): make the group membership resolver consult code validity for every non-`done` member, `pending` included. Rejected: it puts git and artifact reads into a state-only resolver that the FINISH fence also calls, and widens preservation to `pending`, which the stale-preservation decision (#2639) deliberately excluded.
- Selected: A and B together. The issue offers them as "alternatively, or additionally". A follows the approved retained-sibling pattern verbatim, so the retained `done` stays subject to kickback restaging and to the FINISH fence's re-validation at current HEAD. B reuses the serial walk's probe unchanged, so a code-valid stale member is preserved with the same `verdict_freshness` evidence on either path, and an in-surface change still dispatches.
