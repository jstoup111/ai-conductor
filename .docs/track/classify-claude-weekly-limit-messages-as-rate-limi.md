# Track: Classify Claude weekly-limit messages as rate limits

Track: technical

Scope boundary: Small fix for #1006, approved by the operator on 2026-09-06 (delegated). The slice is the Claude adapter's rate-limit *classification* vocabulary and its regression coverage. The general rate-limit policy the issue originally asked for — budget-preserving retries, deadline-aware coordinated backoff, and episode entry — already shipped, as the issue's 2026-08-13 scope refresh records; the only reproducible gap left is that the classifier recognizes session and usage wording but not weekly wording, so the observed message falls through as an ordinary failure. Retry-policy behaviour, the wait-duration derivation, the reset-time and timezone deadline parsing, the episode coordinator, and the Codex adapter are all outside this slice.

This is an internal provider-adapter correction with no product requirement behind it; acceptance criteria live in technical stories rather than a PRD.

The operator approved widening the recognized quota-period vocabulary over adding a single literal "weekly" alternative on 2026-09-06 (delegated). A single literal closes today's message and leaves the same defect class open for the next period word the CLI prints; a bounded period vocabulary behind the existing anchors closes the class without loosening the anchors that keep prose from matching.

Scope check: A — consumer-facing (the Claude provider adapter runs in every repository that installs the harness; no self-host, daemon-only, release-gate, or repository-convention signal fires); B — n/a (no new skill); C — provider-agnostic in outcome. The edited pattern is Claude-specific message text, and the equivalent Codex seam already exists and already recognizes that host's own usage-cap wording, so no host is left silently degraded and no capability is added on one host only. No catalog registration is required.

Verified foundation: `src/conductor/src/execution/claude-provider.ts` holds `SESSION_LIMIT_RE`, whose period alternation is exactly `session|usage`, so "You've hit your weekly limit · resets 9pm (America/New_York)" matches none of its three shapes. `RATE_LIMIT_RE` is `rate limit|429|overloaded` and is consulted only when the exit code is non-zero, so it does not rescue the message either. The classification site tests `SESSION_LIMIT_RE` regardless of exit code and folds the result into `rateLimited`, into the `success` computation, and into the branch that derives `waitSeconds` and `deadline`. `parseRateLimitWaitSeconds` already parses "resets 9pm (America/New_York)" through its bare-hour-with-timezone path, so the deadline works the moment the message is recognized. `detectsSessionLimit` is exported as a test helper and currently has no callers. `src/conductor/test/execution/claude-provider.test.ts` mocks the subprocess boundary and drives `ClaudeProvider.invoke`; `src/conductor/test/acceptance/daemon-rate-limit-episode-coordinator.acceptance.test.ts` already drives the real classification call site through the real conductor step loop for the session-limit message. No page under `docs/`, `HARNESS.md`, or the skill catalog describes the recognized limit wording, so this change leaves no stale reader-visible documentation.
