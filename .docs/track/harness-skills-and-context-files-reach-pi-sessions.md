# Track: Harness skills and context files reach Pi sessions like other hosts

Track: technical

Scope boundary: Close three gaps so a Pi-dispatched step matches a claude/codex dispatch. (1) Skill invocation: Pi's catalog invocation prefix becomes `/skill:` (verified on pi 0.84.3). The engine refuses before spawning when the invoked skill does not resolve in Pi's skill roots, because Pi passes an unknown `/skill:<name>` through as plain text. (2) Behavioral rules: the Pi adapter injects HARNESS.md via `--append-system-prompt`, the Pi equivalent of Claude's SessionStart hook. (3) Project skills: the Pi adapter loads the project's `.agents/skills/` via `--skill`, because non-interactive Pi ignores untrusted project skill dirs. The approach keeps Pi's native discovery (global `~/.agents/skills`, `AGENTS.md`/`CLAUDE.md` context files, the operator's own Pi skills) and adds only what Pi cannot reach itself. Also in scope: `bin/install --providers` accepts `pi`, reports its readiness, and stays idempotent without disturbing the claude/codex catalog links; the catalog's Pi home variable is corrected to `PI_CODING_AGENT_DIR` (default `~/.pi/agent`); `disable-model-invocation` keeps working under Pi; the multiprovider host-difference docs and the HARNESS.md skill-invocation list gain Pi's row. Excluded: the `reviewPolicyCatalog` capability and Pi build_review (moved to follow-up intake #2852, and the catalog owner map is re-pointed from #1888 to #2852), self-host provider homes (#1887), read-only review/containment (#1886), model selection (#1885), telemetry (#1889), smoke parity (#1890), install-time mutation of global Pi config.
