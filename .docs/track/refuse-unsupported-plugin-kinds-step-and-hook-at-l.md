# Track: Refuse unsupported plugin kinds at load

Track: technical

Scope boundary: Small fix for #1931, approved by the operator on 2026-09-06 (delegated). Retire the two plugin kinds that no runtime seam retrieves, refuse them at manifest validation with a message that names the kind as unsupported, and add a guard binding the remaining kind list to real retrieval sites. Designing or building a step-plugin or hook-plugin execution seam is outside this slice, as is any change to how supported kinds are discovered, registered, selected, or invoked.

This is an engine type-surface and manifest-validation correction; acceptance criteria live in technical stories rather than a PRD.

The filer offered two candidate resolutions: wire a real seam per kind, or drop the kinds and refuse them. A third alternative not derived from the filer's sketch was weighed — keep the kinds registered but emit a startup warning naming the registered-but-unreachable plugin — and rejected: it preserves the false promise in the type surface, leaves a registry entry nothing can consume, and turns a load-time refusal into a warning an operator can ignore. Wiring a seam was rejected as out of proportion: there is no consumer, no designed contract for what a step or hook plugin would receive, and inventing one needs a decision this issue leaves open. Refusal with a named error is the honest fix and is what the operator's delegated instruction authorizes; the kinds can be reintroduced with their seam when a real consumer exists.

Scope check: A — consumer-facing. No repo-only signal fires: this is not self-host, daemon, sandbox, this repository's validation or release gates, its CI, or a convention only this repository has. A repository that installed the harness, has no daemon and no self-host build, still benefits, because plugin manifests are discovered from that repository's own `.ai-conductor/plugins/` directory. B — n/a, no new skill. C — provider-agnostic; the manifest schema and registry carry no provider-specific path, variable, or capability. Registration: no catalog, model-table, or `HARNESS.md` rule entry is required; documentation upkeep is satisfied on the page that already documents plugin manifests for consumers, `docs/contributing/extending.md`. That page sits under `docs/contributing/` even though the change is consumer-facing, because it is the canonical page for plugin manifest authoring and already carries the visualizer plugin contract; splitting plugin-kind guidance onto a second page would leave the existing contract stale.

Verified foundation: `src/conductor/src/types/plugin.ts:8` declares `PluginKind` with six members and `:13-20` repeats them in `VALID_PLUGIN_KINDS`. `validateManifest` in `src/conductor/src/engine/plugin-manifest.ts:51-56` admits any member of that list, and `discoverPlugins` in `src/conductor/src/engine/plugin-loader.ts` registers whatever validates, skipping a `PluginManifestError` with a `console.warn` naming the plugin directory. An exhaustive read of the registry retrieval sites confirms four kinds are consumed and two are not: `llm_provider` at `src/conductor/src/engine/provider-runtime.ts:104`, `ui_renderer` at `src/conductor/src/index.ts:1414`, `visualizer` at `src/conductor/src/index.ts:257`, and `memory_provider` at `src/conductor/src/engine/config.ts:2710`. Issue #1516, which the filer cited as covering `visualizer`, is closed and that seam is live. Outside `src/conductor/src/types/plugin.ts`, the strings `step` and `hook` as plugin kinds appear at exactly one other site in the repository, `src/conductor/test/engine/plugin-registry.test.ts:123`; no documentation page and no shipped example manifest declares either kind. The self-host release gate's breaking-surface classifier in `src/conductor/src/engine/self-host/release-gate.ts:123-139` matches only `bin/conduct`, `bin/install`, hook paths, settings JSON, and removed or renamed skill directories, so this change touches no surface that requires a migration block.
