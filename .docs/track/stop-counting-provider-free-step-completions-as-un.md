# Track: Provider-free step completions are not dispatches

Track: technical

Scope boundary: Small fix for #1906, approved by the operator on 2026-09-06 (delegated). Correct the shared dispatch-metering projection so a completed step that invoked no provider contributes to neither the provider-dispatch count nor the unmetered-dispatch count, while an invoked provider call with no usable usage stays explicitly unmetered. The correction is reader-side only: it must reclassify already-retained event ledgers on replay. Emitter changes to the `step_completed` payload, the `runFinishPublication` result shape, KPI aggregate policy, and the partial-feature exclusion rule are outside this slice.

This is an internal engine measurement correction; acceptance criteria live in technical stories rather than a PRD.

The operator approved reader-side reclassification over stamping a new provider-invocation field on `step_completed`, on 2026-09-06 (delegated). The deciding constraint is the issue's own last desired outcome: replaying PR #1893's already-retained events must report 14 dispatches, 14 metered and 0 unmetered. A new emitter field cannot be present in events that were written before it existed, so only a reader-side rule can satisfy that outcome. The evidence set the reader keys on — token usage, actual provider, preferred provider, or model — was approved on the same date and for the same reason: those four fields are the only provider attribution the completion record ever carries, and all four originate in provider execution.

Verified foundation: `DispatchMeteringTracker.observe` (`src/conductor/src/engine/dispatch-metering.ts:22-58`) suppresses a `step_completed` record only when its `step` and `actualProvider` match a previously observed successful invoked `provider_attempt`; every other completion falls through to `toObservation` and is returned. `computeCostRollup` (`src/conductor/src/engine/cost-rollup.ts:226-241`) turns each returned observation into a dispatch through `addDispatch` (`cost-rollup.ts:129-150`), which increments `unmetered.count` whenever the record carries `unmetered: true` or classifies as unmetered. The engine stamps `unmetered: true` on every completion whose step result has no token usage (`src/conductor/src/engine/conductor.ts:11412`). Three step paths reach that stamp with no provider attribution at all: `runFinishPublication` returns only `{ success, publicationDisposition }` (`conductor.ts:2847-2878`), `publishBuildReviewPass` returns only `{ success, output }` (`src/conductor/src/engine/step-runners.ts:2739-2761`), and a clean native rebase returns `{ success: true }` without reaching the conflict resolver (`conductor.ts:12333-12351`). PR #2063 (`36ef5ec38`) introduced the tracker and closed the double-count for completions that do carry `actualProvider`; it does not reach any of these three, which is why the observation in #1906 still stands on the current default branch. The second consumer, `OtelVisualizer` (`src/conductor/src/engine/otel/otel-visualizer.ts:406-411` and `:506-517`), passes the same observation's presence to `MetricsRecorder.onStepClose` as its `recordDispatch` flag (`src/conductor/src/engine/otel/metrics.ts:87-104`), so one reader-side rule keeps the exported counter and the committed rollup in agreement by construction.
