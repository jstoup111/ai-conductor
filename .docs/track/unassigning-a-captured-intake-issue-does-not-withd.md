# Track: Unassigning a captured intake issue does not withdraw it from claim

Track: technical

Scope boundary: Claim-side only, narrow (operator-delegated acceptance; recorded here as the binding breadth). `compose claim` serves a `github-issues` candidate only when the machine owner is currently among the issue's assignees. The check sits at the single point where the delivery guard serves a candidate, so the normal pending queue, stale-claim reaps, and `unclaim`/`requeue`-recovered envelopes are all covered. A skipped candidate stays `pending` in the ledger and in the inbox, so reassignment brings it back on a later claim with no ledger edit. Each skip is reported on stderr with the issue reference and the reason. An assignment read that fails, or a machine owner that cannot be resolved, also skips the candidate and is reported as unknown; the candidate is never forgotten or dropped. Included: `delivery-guard.ts` (the serve-time check), `github-issues.ts` (one shared current-assignees read, reused by the existing write-back authorization), and `engineer-cli.ts` (wiring the existing machine-owner resolver into the claim guard). Excluded: poll and capture (still `--assignee @me`), the `requeue`/`unclaim` verbs themselves, the daemon backlog, non-`github-issues` sources, the claim JSON output shape, any ledger status or schema change, any new event variant or config key, and `forget`'s handling of a 404 when stripping a label the issue never had.

Approaches weighed (filer hypotheses entered as candidates, not privileged):

- A (selected; filer hypothesis 1 with keep-pending): check current assignment at serve time inside the delivery guard, beside the existing closed-issue probe. An unassigned or unknown candidate is held and released back to the inbox, exactly as the guard already holds an unknown-PR-state candidate, and the skip is reported. One check covers every path that can serve a candidate, needs no ledger mutation, and keeps the entry's FIFO position, so reassignment needs nothing but the reassignment.
- B (filer hypothesis 2): forget an unassigned entry and let poll recapture it on reassignment. Rejected: it rests on poll no longer suppressing a forgotten ref (unverified), loses the entry's `capturedAt` order and attempt history, and turns a reversible operator signal into a destructive ledger write.
- C (alternative not from the filer): a poll-side sweep that withdraws ledger-pending refs whose issue is no longer assigned, modelled on the closed-issue reconciliation sweep. Rejected: claim between sweeps still serves a withdrawn issue, stale-claim recovery at claim time bypasses it, and it adds a second place that decides claimability.

Internal intake-engine behavior with no product requirements; acceptance criteria live in stories (intake jstoup111/ai-conductor#3540).
