# Track: Stamp released harness version on OTel trace resource

Track: technical

Scope boundary: Small fix for #2235, approved by the operator on 2026-09-06 (delegated). Add one released-harness-version resource attribute to the traces signal, resolved at the two supported OTel start boundaries from the running engine module, and leave the metric resource attribute set unchanged. Publish-time capture of the release into the engine dist sidecar, backfill of already-published dists, backend span-metrics dimension configuration, dashboard changes, and every other resource attribute are outside this slice.

This is internal telemetry identity for the shipped engine; acceptance criteria live in technical stories rather than a PRD.

Approach, approved by the operator on 2026-09-06 (delegated): stamp the OTel-standard `service.version` on the trace Resource, sourced through the engine's existing module-relative `resolveHarnessVersion` probe and threaded through the same start-context seam the engine dist id already uses. The filer's first hypothesis (a conductor-namespaced `conductor.engine.semver`) was weighed and rejected: a private attribute name is invisible to the default service-version grouping every OTel backend already offers, and the operator's follow-up note asks explicitly for a value any consumer can group by. The filer's second hypothesis (record the release into the dist sidecar at publish time and read it back) was weighed and rejected for this slice: it changes the publish script, needs a new sync sidecar reader plus a fallback for every already-published dist, and lands outside the Small tier. Its one advantage is fidelity — the module-relative probe reports the harness checkout's current release rather than the release at the dist's source commit, so the two disagree only inside the window between a release merge and the next engine publish. That window is accepted here and is the same value `ai-conductor --version` already prints, so the two identities cannot drift apart.

Event spine: Channel? no — no watcher, poller, sidecar file, bespoke log, or artifact-stamped timestamp is introduced. The change adds one attribute to a Resource already exported by the existing OTel visualizer, which is itself an ordinary consumer of the event bus. Concern: durable identity of the running engine, not an occurrence in time. Verdict: no spine change, no new channel, no ADR required. Exception: none needed.

Scope check: A — consumer-facing. No repo-only signal fires: nothing under the self-host, live-boundary, or sandbox machinery is touched, no repository validation or release gate is touched, no workflow or custom-step configuration is touched, and the `VERSION` file being read is the installed harness's own, which every consumer install carries and already surfaces through `ai-conductor --version`. A repository that installed the harness, has no daemon and no self-host history, still benefits: its interactive runs export the release too. B — n/a, no new skill. C — provider-agnostic; no Claude- or Codex-specific behavior is involved. No catalog registration is required. The reader-visible documentation for this surface is the `otel` section of the configuration reference; it is delivered by this repository's maintain-documentation step rather than by a plan task.

Verified foundation: `src/conductor/src/engine/otel/resource.ts` builds a signal-scoped Resource — the metrics branch returns exactly five feature-stable attributes and returns early, while the traces branch adds `conductor.run.id` and `conductor.engine.version`; `normalizeIdentity` maps an omitted property to `not-supplied` and an empty or undefined one to `unresolved`. `src/conductor/src/engine/otel/wire.ts` declares `OtelVisualizerStartContext` with `branch` and `engineVersion` as required `string | undefined` members. `src/conductor/src/engine/otel/otel-visualizer.ts` projects that start context into the resource context behind an own-property guard and builds both signal scopes from it. `src/conductor/src/index.ts` and `src/conductor/src/daemon-cli.ts` are the two supported start boundaries; both already resolve the engine dist id from their own `__dirname`, and both sites are inside `async` functions. `src/conductor/src/engine/version-report.ts` already exports `resolveHarnessVersion(moduleDir, readText?)`, which probes three and four levels above the module directory for a semver-shaped `VERSION`, returns `0.0.0` when none is readable, and never throws. `src/conductor/src/types/plugin.ts` declares the shared `VisualizerStartContext` with optional identity members. The approved OTel observability ADR's 2026-08-28 amendment fixes the signal-scoped Resource contract; adding a trace-only attribute conforms to it and requires no amendment.
