# Track: Rejected build_review reviewer output is retained for diagnosis

Track: technical

Scope boundary: The issue's four desired outcomes, as filed (composer-run, operator pre-authorized 2026-10-10). In scope: (1) every `build_review` reviewer response the engine rejects as `invalid-structured-result` — built-in rubrics (`testQuality`, `security`) and installed custom rubrics (for example `eventSpine`) — is retained on disk as one record per rejection, keyed by lap, rubric, and a per-lap attempt ordinal, and survives a replay of the same lap; (2) a custom rubric's dispatched reviewer prompt is retained beside its lap artifact, as the built-in `<rubric>.prompt.txt` already is; (3) for a custom rejection whose payload cites source regions, the record carries, for every cited region, the engine's recomputation against the frozen lap input; (4) retention is best-effort and never changes the verdict, the rejection reason or detail, retry routing, the lap input digest, or mechanical-fault accounting. Excluded: changing what the engine accepts or rejects; retaining accepted responses; any change to the mechanical-fault allowance, reduced-coverage recording, or cache; pruning policy for retained records beyond the existing per-worktree `.pipeline/` lifecycle; a built-in per-region comparison (built-in source-region authority is already retained verbatim in the built-in `<rubric>.prompt.txt`).

Engine-side diagnostics for operators — no product requirements; acceptance criteria live in stories.

Verified basis (read 2026-10-10 at main `09eb5903bf`):
- Built-in rejections are all decided inside `dispatchBuildReviewRubric` in `src/conductor/src/engine/step-runners.ts` (the `structuredResultFailure`, non-object, and failed-validation returns), where the provider's `output` and `finalStructuredResult` are still in scope; each returns `makeBuildReviewDispatchFailure(..., { cause: 'invalid-structured-result', rejection })` and the payload is then discarded. The coordinator (`build-review-coordinator.ts` ~785–820) only sees the failure value. Confidence 95% (verified).
- Custom rejections are decided in `dispatchInstalledBuildReviewPolicy` (`settleCustomStructuredRejection` and the `unsupported-policy` branch), which already emits `build_review_rubric_infrastructure_failure` with `cause` and `rejection` but writes no payload and no prompt. Confidence 95% (verified).
- A custom-policy lap `rm -rf`s `.pipeline/build-review/<lapId>/` before every replay of the same head-derived lap id, so anything written only inside the lap directory is lost on the next attempt — which is why the issue's three attempts left one 641-byte `eventSpine.json`. Confidence 95% (verified).
- The lap input-integrity gate digests the pipeline evidence root; files created after capture are ignored, but a file present at capture and rewritten during the lap marks the lap `review-input-mutated`. `BUILD_REVIEW_ENGINE_OWNED_LAP_WRITES` (`build-review-input-integrity.ts`) is the existing exclusion list for engine-owned writes. Confidence 95% (verified).
- `admitBuildReviewCustomSourceRegions` stops at the first failing region, and on rejection the custom diagnosis is run with an empty admitted set, so every cited region is reported as "must exactly match an admitted frozen source region" regardless of which one actually failed. Confidence 90% (verified by reading; not reproduced).

Event spine (per `.agents/skills/event-spine/SKILL.md`): channel — yes, a new evidence file; concern — durable state (what the reviewer returned), while the occurrence is already carried by `build_review_rubric_infrastructure_failure`; verdict — exception C evidence artifact plus one additive optional field on that existing event variant naming the retained record's path; no new event variant, no timestamp stamped into the record.

Scope check (per `.agents/skills/scope-check/SKILL.md`): A — consumer-facing engine behavior (`build_review` runs in every installing repository; no rule text changes); B — n/a, no new skill; C — provider-agnostic, written by the engine from the normalized invocation result for every provider.

Chosen approach A (engine-written per-rejection evidence record under a lap-keyed directory outside the replay-cleared lap directory, excluded from the lap input digest, pointed to by an optional field on the existing infrastructure-failure event) over B (filer-adjacent: carry the raw payload on the event itself — unbounded payloads in `.pipeline/events.jsonl` exceed the single-write atomicity bound the event-spine skill's exception B describes and bloat every bus consumer) and C (write the payload into the existing `<rubric>.json` lap artifact or the same lap directory — the lap directory is cleared on every replay so earlier attempts are lost, and the branch artifact's strict exact-key parser would have to change).
