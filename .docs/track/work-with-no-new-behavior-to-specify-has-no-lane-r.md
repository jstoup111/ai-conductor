# Track: Maintenance-change lane for refactors, deletions, and dependency upgrades (#1790)

Track: technical

Scope boundary: Minimal, per-feature. Make a no-new-behavior change (refactor, deletion, dependency upgrade) runnable through the harness on existing machinery: enable this repository's `feature_applicability` toggle; document a maintenance-change recipe in the DECIDE skills (technical track, a `.docs/applicability/<stem>.md` marker declaring `acceptance_specs`/`manual_test` inapplicable with a reason naming the change class, Verify-only or removal-shaped plan tasks); and correct stale references to the retired `scope`/`completeness`/`tautology` rubrics and to the technical track skipping `prd_audit`. Excluded: any new gate behavior; a structured change-class field, grammar, event, or shipped-record section (deferred until a gate needs to branch on it); per-task classification; new plan task kinds; changes to `test_suite`, integrity checks, release-metadata, `build_review`, `prd_audit`, or scope containment. Inferred frictions — scope containment flagging lockfile fallout and `prd_audit` grading fallout OVER_SCOPE/PLAN_GAP — are deferred to intake issues filed only when observed on a real run.

Rationale: the issue's two named gates (`build_review` scope/completeness) were retired by adr-2026-08-22-one-owner-per-review-question and #1789 shipped the per-feature declaration surface, so the remaining gap is an unrecorded, undocumented lane, not engine behavior. Approved approach: recipe on existing machinery (class carried in the merge-attributed applicability reason). Rejected: a structured `Class:` field expanding into declarations (machinery with no consumer under minimal scope; the promotion path once a gate must branch on class); new `Track:` values (`parseTrack` silently defaults unknown values to `product`, and track answers the PRD question, not the change-class one).
