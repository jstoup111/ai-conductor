# Track: Show autoresolve guard and suite gate progress

Track: technical

Scope boundary: Small observability fix for jstoup111/ai-conductor#2762, approved by the operator on 2026-09-28 (delegated). After the mergeable-sweep autoresolve finishes its tier-2 resolution, the acceptance-guard stage and the suite gate run before the lease push and are silent when they pass. This slice makes the passing acceptance-guard stage, the suite-gate start, and the suite-gate pass visible in the daemon log and on the event spine, each naming the PR and the resolution worktree, with the suite duration on the pass. Failure logging, escalation, and the escalation stage names are unchanged. Out of scope: suite progress streaming or heartbeats while the suite runs, a suite timeout, the feature pipeline's test_suite step, OTel export, and terminal rendering of the new event.

This is internal engine telemetry read by the operator in the daemon log and by event-spine consumers; there is no product surface, so acceptance criteria live in technical stories rather than a PRD.

Event spine verdict: Channel? yes (a new occurrence signal). Concern: occurrence (a stage started or passed at a point in time). Verdict: extend the union with one new ConductorEvent variant emitted through the existing injected emitter. Exception: none. The daemon already hands resolveConflictingPr a feature-scoped forwarding emitter that persists to the feature ledger and forwards to daemon observers, so no new sink, file, or ledger is added. The issue's hypothesis of reusing the pipeline test_suite event shape was weighed and discarded: step_started and step_completed are keyed by pipeline StepName, and test_suite_verification carries evidence freshness, not a start or pass occurrence, so neither fits an autoresolve stage without distorting existing consumers. The daemon log lines use the same injected log function that already writes the tier2 outcome and suite-gate failure lines, not a new channel.
