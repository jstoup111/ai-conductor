# Track: Fail closed when build_review cannot resolve which plan

Track: technical

Scope boundary: Small fix for #2179, approved by the operator on 2026-09-06 (delegated). Separate "no plan work exists" from "cannot determine which plan" in the shared feature-plan resolver, and make only the build_review step fail closed on the second case. Every other caller of the resolver keeps its current behavior byte-for-byte. Rewriting the resolution ladder itself, changing how the active plan is recorded, adding retry routing or a new halt class, and reworking the empty-scope rubric policy are outside this slice.

This is an internal engine gate correction with no product requirements; acceptance criteria live in technical stories rather than a PRD.

The operator-delegated decision on 2026-09-06 was to add a discriminated selection helper beside the existing path-returning resolver rather than change that resolver's return type. Changing the return type would touch all fourteen existing call sites for a defect that lives at exactly one of them; the additive helper keeps the blast radius at two production files while still giving build_review the distinction it needs. A needs-human refusal was chosen over a kickback because no step re-dispatch can change the input: the plan corpus and the feature slug are unchanged by another lap, and routing back to plan authoring from the daemon is not a supported destination.

Scope check: A — consumer-facing. No repo-only signal fires: the change touches no self-host or daemon machinery, no repository validation or release gate, no CI workflow, and no convention private to this repository. The build_review gate ships inside the engine and runs in every project that installs the harness, so a consumer with no daemon and no history still benefits. B — n/a, no new skill. C — provider-agnostic: the refusal is decided in the engine before any grader is dispatched, and no provider-specific code path is touched.

Verified foundation: `resolveFeaturePlanPath` in `src/conductor/src/engine/artifacts.ts:733` walks a ladder — engine-recorded active plan, then singleton plan corpus, then a plan whose stem equals the feature description — and returns `undefined` for both an empty corpus and an unresolvable multi-plan corpus. `runBuildReview` in `src/conductor/src/engine/step-runners.ts:2572` prefers a caller-supplied plan override, otherwise calls that resolver, and maps every `undefined` to `publishBuildReviewPass` (`step-runners.ts:2739`), which writes a durable `PASS` verdict artifact and stamps it. Its own comment claims the resolver "fails closed on ambiguity", which the resolver does not do. The sibling `runCoverageBinding` (`step-runners.ts:2447`) already treats the same `undefined` as a step failure, and `runCoverageBinding` at `step-runners.ts:2566` shows the established `refusal: { kind: 'needs-human' }` shape, which `conductor.ts:10108` turns into a halt marker and a loop halt. `adr-2026-09-06-engine-owned-test-quality-scope` decision 7 blesses the empty-scope PASS for a genuinely empty scope and says nothing about plan-resolution ambiguity, so no approved decision is amended.
