# Track: Architecture review never checks seam conformance

Track: technical

Scope boundary: Fix for #1995, breadth set by the issue's three desired outcomes and the operator's Small-tier request, accepted under the operator's delegation for routine DECIDE acceptances (2026-11-15). The shipped `architecture-review` skill gains a seam-conformance check in two passes: the pre-stories DECIDE pass (§4 Architectural Alignment, which also runs in full in Medium lightweight mode) and the SHIP as-built pass (§12, inside the existing `adrCompliance` check). When a reviewed design or diff has production code reach an external system directly while an APPROVED ADR of the consuming project defines the boundary interface for that system, the review raises a blocking finding. Routing through that boundary, working inside the boundary's own implementation, or introducing a new boundary together with its own ADR passes, provided that ADR covers a system no APPROVED ADR already gives a seam, or supersedes the existing seam ADR through the normal human-approved lifecycle. A production call the diff reroutes onto a direct path counts the same as an added one. The seam inventory comes only from the consuming project's APPROVED ADRs; a project with no such ADR gets no seam finding. The skill text names no repository-specific boundary, port, module, or file path. Excluded: mechanical import-direction and layering rules (owned by a project linter, #1988); the batch-boundary review (§10); any engine, schema, configuration, or as-built check-policy change; any new agent persona; any change to this repository's own boundaries (#1989).

This is harness review behavior with no end-user product surface; acceptance criteria live in technical stories rather than a PRD.

Approach chosen: amend the skill text only (the filer's hypothesis, which won on merits). The check's core questions are whether a call reaches an external system and whether an approved boundary governs it. Both are judgement calls that need project-specific knowledge, so under the repository's design principle they belong in the reviewer's judgement. The engine already does the bookkeeping that judgement needs. `resolveAsBuiltPolicy` turns `adrCompliance` off when the project has no APPROVED ADR. `resolveAsBuiltReferences` accepts a BLOCKED finding whose governing reference is any APPROVED ADR decision in the worktree. The existing `REMEDIABLE` and `DESIGN` classes route the finding. The as-built instruction is diff-first: the reviewer looks for a governing seam ADR only for an external-system call the diff introduces or reroutes, so a diff with no such call costs no ADR reading.

Seam inventory is ADRs only, not diagrams. The issue's outcome says "ADRs/architecture artifacts", but an as-built BLOCKED finding can only cite an `adr-decision` or `plan-task` governing reference (`AsBuiltGoverningReference` in `src/conductor/src/engine/as-built-contract.ts`), and diagrams carry no APPROVED status. A seam that exists only in a diagram therefore cannot back a blocking finding; diagrams may still help the reviewer locate a seam an ADR defines, and diagram drift stays with `diagramDrift`.

Rejected alternative (not from the filer): an engine-level `seamConformance` as-built check with its own tier policy, fed by a machine-readable boundary declaration added to the ADR template and projected into the as-built input. It makes the inventory deterministic, but no existing ADR in any consumer project carries the declaration, so the check would be silently off everywhere until projects re-tag their ADRs. It also adds a configuration key and a projection contract change for a question whose hard core is still an LLM judgement. Rejected alternative (not from the filer): a `build_review` rubric that checks seams per task. BUILD-time review judges each task's diff against its plan task, so the rubric would repeat the same ADR-derived judgement per task and add per-task cost, and the issue names architecture review as the gap; the as-built pass already runs once per feature at every tier. Rejected alternative: dispatch the `cto-architecture` persona inside the per-feature flow as a standards reviewer. The issue's own analysis notes it would re-litigate what the linter settles, and it adds a dispatch to every feature for a check the existing review already has the inputs for.
