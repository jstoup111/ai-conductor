# Track: Stop refuting blanket environment-denial claims (#1298)

Track: technical

Scope boundary: Small fix for #1298, approved by the operator on 2026-09-06 (delegated). Narrow the environment-claim audit so an assertion that the environment denies an unbounded set of commands is left alone, and make each refutation state the proposition it disproved and the evidence for it. The audit's existing asymmetry, its provider policy, its fence-derived deniable-operation set, and its failure semantics in the self-host candidate-safety wrapper are preserved unchanged. Rewriting the write fence's own over-blocking behavior (`has_write_shape` plus the whole-payload `>` grep) is a separate defect and is outside this slice; so are new audited operations, scope-aware natural-language parsing of claims, and any new telemetry.

This is self-host engine machinery with no product-facing behavior; acceptance criteria live in technical stories rather than a PRD.

Approach: the operator-delegated decision on 2026-09-06 selected a negative guard over sentence-scope detection. A blanket assertion ("blocking all Bash commands", "rejecting every Bash call") is recognized as a claim class the engine's operation-name evidence cannot bear on, and the operation-specific refutation is suppressed for that output. The rejected alternative — inferring the grammatical scope of the denial and refuting only the narrow reading — needs natural-language scope analysis the engine cannot perform deterministically, which is the failure mode the issue reports. The accepted cost of the negative guard is that an agent can avoid refutation by asserting a total block; that is the documented asymmetry (refute only what can be positively disproved), and a claim left alone is still handled by the step's ordinary failure path.

Scope check: A — harness-repo-only (the change is confined to `src/conductor/src/engine/self-host/`, a Step 1 repo-only signal; the audit runs only on self-host dispatches); B — n/a (no new skill); C — provider-agnostic (the provider table's `claude`/`codex` entries and their meanings are untouched, and the guard is provider-independent). No catalog registration is required. The reader-facing descriptions of this audit already live in the settings-and-hooks reference and the stalled-or-stuck-feature runbook; those are the canonical pages this repository's documentation-upkeep rule points at for the delivered change.

Verified foundation: `environment-claim-audit.ts` requires an environmental cause, a blocking assertion, and an audited-operation regex to co-occur on ONE line before a claim exists, then refutes it whenever the generated fence script carries no token for that operation. `writeFenceDeniableOperations()` derives that set by scanning `generateFenceScript`, and the `gh` entry's fence token is `\bgh\b`, so a deny-all failure mode — in which no operation name would ever appear in the fence — is refuted on evidence that cannot bear on it. The failure mode is real, not fabricated: `write-fence.ts` treats any `>`/`>>`/`&>` redirection as a write shape, and its escape hatch greps the whole tool-call JSON for `>` before reaching `FENCE BLOCK: write target could not be determined`. `conductor.ts` calls `auditEnvironmentBlockerClaims` inside `withSelfHostCandidateSafety` and converts a non-null message into a failed attempt, so a false refutation costs a dispatch attempt out of the retry budget.
