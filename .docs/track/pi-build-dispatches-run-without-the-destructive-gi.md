# Track: Pi build dispatches run without the destructive-git guard

Track: technical

Scope boundary: Pi provider adapter parity with the existing engine git guard (adr-2026-09-23-engine-git-guard-on-agent-path D2, D3, D10), covering intake issues jstoup111/ai-conductor#3002, #2895 and #2854 together (operator decision: one spec, #3002 as the source ref). In scope: a Pi writable dispatch whose working directory is an engine-prepared worktree gets the worktree guard first on the child `PATH`, is refused before launch when the guard cannot be verified or repaired, and reports `gitGuardInstalled` on its result; Pi review dispatches stay exempt exactly as Claude and Codex reviews are; a Pi dispatch outside a prepared worktree (no repository, or a linked worktree the engine never prepared) launches unguarded and reports so; and an opt-in Pi live guard smoke excluded from the default suite. Excluded: changes to the guard script, its refusal matrix, or `ensureGitGuardForDispatch`; Claude and Codex adapters; Pi's read-only review tool set; a Pi-specific shell-tool extension; defeating `PATH` shadowing by Pi's own agent `bin` directory (an ADR D10 recorded limit); and the `credentialed:pi` smoke-capability gating itself (#1890).

Provider-adapter safety parity with no product requirements; acceptance criteria live in stories. Approach: reuse the existing `ensureGitGuardForDispatch` / `withGitGuardPath` seam in the Pi adapter. Verified against the installed Pi (`@earendil-works/pi-coding-agent`, `dist/core/tools/bash.js:66,136` and `dist/utils/shell.js:115-126`): Pi's bash tool spawns with `{ ...process.env, PATH: <pi agent bin>:<inherited PATH> }`, so a guard prepended to the Pi process `PATH` is what Pi's shell resolves. Rejected alternatives: a Pi extension wrapping the bash tool (new Pi-specific mechanism for a property the shared seam already delivers), and removing `bash` from Pi build dispatches (breaks build work).
